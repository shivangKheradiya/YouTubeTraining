# 🔄 Order of Evaluation

## Overview
In C, the **order of evaluation of subexpressions** within a larger expression is **not specified by the language standard**. This gives compilers the freedom to rearrange expressions to generate more efficient machine code.  

While this flexibility improves performance, it also means that programmers must **never rely on a specific evaluation order** unless explicitly guaranteed by the language.

---

## 🛠️ Precedence vs. Evaluation Order
- **Operator precedence** defines which operations are grouped together.  
- **Evaluation order** defines the sequence in which those grouped operations are executed.  
- C guarantees precedence but **does not guarantee evaluation order** for subexpressions.  

---

## 📊 Precedence Table (Simplified)

| Precedence Level | Operators                                |
|------------------|------------------------------------------|
| Highest          | `( )`, `[ ]`, `->`                       |
|                  | `!`, `~`, `++`, `--`, `(type)`, `*`, `&`, `sizeof` |
|                  | `*`, `/`, `%`                            |
|                  | `+`, `-`                                 |
|                  | `<<`, `>>`                               |
|                  | `<`, `<=`, `>`, `>=`                     |
|                  | `==`, `!=`                               |
|                  | `&`                                      |
|                  | `^`                                      |
|                  | `|`                                      |
|                  | `&&`                                     |
|                  | `||`                                     |
|                  | `?:` (ternary operator)                  |
|                  | `=`, `+=`, `-=`, `*=`, `/=`, etc.        |
| Lowest           | `,` (comma operator)                     |

---

## ✔️ Example
```c
x = f1() + f2();
```
- This expression does **not** guarantee that `f1()` will be called before `f2()`.  
- The compiler may choose the order based on optimization strategies.  

---

## 📌 Key Notes
- Do **not** write code that depends on the order of evaluation of subexpressions.  
- Use **parentheses** to clarify precedence, but remember they do not enforce evaluation order.  
- If a specific order of execution is required, **separate the operations into distinct statements**.  

---

## 📝 Safer Alternative
```c
int a = f1();
int b = f2();
x = a + b;   // guarantees f1() is called before f2()
```

## 🎯 Learning Goals
By the end of this section, you will:
- Understand the difference between operator precedence and evaluation order.  
- Recognize that C does not guarantee the order of subexpression evaluation.  
- Avoid writing code that relies on unspecified evaluation order.  
- Use separate statements when a specific sequence of execution is required.
