# The “Implicit int” Rule

Early versions of C included a feature commonly known as the **implicit int rule** (also called the *default‑to‑int rule*). Under this rule, if no explicit type specifier was provided, the compiler automatically assumed the type **`int`**.

This rule was part of the C89 standard but was **removed in C99** and is **not supported in C++**. Although obsolete, it still appears in older codebases, so understanding it remains useful.

## How the Implicit int Rule Worked

The most frequent use of the rule involved **function return types**. Historically, many C programmers omitted the return type when writing functions that returned an integer. For example:

```c
int f(void) {
    /* ... */
    return 0;
}
```

was often written as:

```c
f(void) {   /* return type int by default */
    /* ... */
    return 0;
}
```

In the second version, the compiler automatically assumed the return type was `int`.

## Implicit int in Parameters and Local Variables

The rule applied not only to return types but also to parameters and local variables. For example, in C89 and earlier, the following function was considered valid:

```c
/* Here, the return type defaults to int, and so do
   the types of a and b. */
f(register a, register b) {
    register c;   /* c defaults to int, too */
    c = a + b;
    printf("%d", c);
    return c;
}
```

Here:

- The return type of `f()` defaults to `int`
- The parameters `a` and `b` default to `int`
- The local variable `c` also defaults to `int`

## Modern C: Avoiding Implicit int

Because the implicit int rule is **not supported** in C99 or C++, its use is strongly discouraged—even when writing C89‑compatible code. Relying on implicit typing can lead to subtle bugs, reduced readability, and portability issues.

**Best practice:**  
✅ Always explicitly specify the type of every function, parameter, and variable.
